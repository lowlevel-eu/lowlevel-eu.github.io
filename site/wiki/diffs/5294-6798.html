== Userinterface ==
 
−
Zur Interaktion mit dem User sind einfache Terminals geplant.
 
−
Später soll es dann auch ein Kernel-Terminal geben, das genau angibt, was geschieht und wie die momentane Situation
 
−
im Kernelspace aussieht.
 
−
Der User hat dann auch die Möglichkeit, den Kernelspace bedingt zu verändern um Probleme zu beheben.
 
−
Es soll aber nur eingeschränkten Zugriff geben, damit der Kernel nicht zerstört wird.
 
−
 
−
== OS-Design ==
 
−
Es soll ein elementarer Hybridkernel angeboten werden.
 
−
Dieser soll auch ein elementares Filesystem haben, damit er die Boot-Files lesen und die entsprechenden Module laden kann.
 
−
Manche Module sollen dabei direkt in den Kernelspace geladen werden (z.B. PIC, erweiterte Speicherverwaltung).
 
−
Alle anderen Module sollen dann im Userspace arbeiten.
 
−
Dadurch soll eine größtmögliche Portierbarkeit auf andere Architekturen ermöglicht werden.
 
−
Außerdem sind dann leichter Erweiterungen und Updates möglich.
 
−
Jeder Task, der einen Syscall anbietet, muss außerdem einen Broadcast-Handler anbieten, damit der Kernel in
 
−
regelmäßigen Abständen die Funktion der einzelnen Tasks gewährleisten kann.
 
−
Wenn der Task nach einer bestimmten Zeit nicht reagiert, wird dieser beendet und automatisch vom Kernel neu gestartet.
 
−
Falls dieser Task zur Interaktion mit anderen Tasks verwendet wurde, wird jedem Task ein Signal geschickt, das ihm sagt, dass
 
−
er seine Informationen noch einmal schicken soll.
 
−
Es sei denn, die Informationen befinden sich noch in einer Liste o. ä., die abgearbeitet wird.
 
−
 
−
== Modulkommunikation ==
 
−
Ein Modul registriert sich im Kernel als Modul an gibt eine Beschreibung ab (meistens den Namen der Hardware die es verwaltet).
 
−
Außerdem muss das Modul einen Speicherbereich angeben den es für Broadcasts vorsieht.
 
−
Ein Modul kann beliebig viele Methoden registrieren; es muss nur eine Beschreibung und die Anzahl an Parametern angeben.
 
−
Wenn es Rückgabewerte gibt, geschieht das über das normale Message-Passing des Kernels.
 
−
Es kann außerdem entschieden werden, ob der Prozess eine Benachrichtigung erhalten möchte, dass sein Auftrag erfolgreich umgesetzt wurde.
 
−
Das funktioniert aber nur, wenn das Modul solch eine Möglichkeit bietet.
 
−
Dadurch ist es möglich, dass die Softwareentwickler zwischen synchroner und asynchroner Kommunikation entscheiden können-
 
−
 
−
== Interprozesskommunikation ==
 
−
Es wird mehrere Möglichkeiten der Kommunikation geben.
 
−
Zum einen gibt es Shared-Memory, Message-Passing und dann noch Message-Queues.
 
−
Beim Shared-Memory, müssen sich die kooperierenden Prozesse selbst um die Synchronisation kümmern.
 
−
Beim Message-Passing bekommt der Emfänger ein Signal, dass eine Nachricht für ihn bereit liegt.
 
−
Diese kann er sich dann in seinen Speicher laden.
 
−
Bei den Message-Queues geschieht es auch nur über Methoden.
 
−
Jede Nachricht wird in einen Puffer in den Kernel geladen.
 
−
Wenn der Sender eine größere Nachricht sendet, dann wird das über mehrere Puffer zwischengelagert.
 
−
Außerdem werden diese großen Nachrichten nur nach und nach in den Kernel geladen.
 
−
Dadurch muss der Prozess länger warten, aber der Kernel bleibt vom Speicheraufwand her gering.
