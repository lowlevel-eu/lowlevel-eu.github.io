=== Invalid TSS ===

== Hardware ==
−
Das [[TSS]] ist ein sehr speicherhungriges Konstrukt, wesegen viele Programmierer auf Software-Multitasking umsteigen. Aber ganz ohne TSS geht es dann doch nicht. Dann nimmt man eben nur ein TSS und ändert die einzelnen Felder je nach Prozess. Damit spart man viel Speicherplatz. Dann hat man im [[Scheduler]] folgendes:
 
−
<asm>
 
−
%define TSS_SELECTOR  0x28
 
−
task_switch:
 
−
  ;alten Zustand sichern
 
−
  ;neuen Prozess suchen
 
−
  ;Einträge im TSS ändern
 
−
  mov ax, TSS_SELECTOR
 
−
  ltr ax
 
−
  ;neuen Zustand laden
 
−
iret
 
−
</asm>
 
−
Ja, gut gedacht, funktioniert aber nicht. Bochs beschwert sich zum Beispiel mit einem gut gemeinten ''LTR: doesn't point to an available TSS descriptor!''. Das Problem: die CPU setzt im TSS das sogenannte busy-Flag in der GDT beim Laden des TSS. Wenn man Hardware-Multitasking verwendet, wofür daa TSS eigentlich gedacht ist, dann ist das kein Problem, da man ja immer wieder ein neues TSS lädt und im alten das busy-Flag automatisch wieder gelöscht wird. Hier wird aber nur '''ein''' TSS verwendet. Deshalb muss das busy-Flag von Hand gelöscht werden:
 
−
 
 
−
<asm>
 
−
;...
 
−
  mov BYTE  [ADDRESS_GDT+TSS_SELECTOR+5], 0x89  ;busy-Flag löschen
 
−
  mov ax, 40
 
−
  ltr ax
 
−
;...
 
−
</asm>

=== __attribute__((packed)) ===
 +
Und wieder macht uns der Compiler ein schönes Codekonstrukt kaputt, weil er structs "optimiert". Folgender Code erstellt einen IDT-Eintrag:
 +
<c>
 +
VOID idt_set_entry(uint8 n, unit16 sel, void* handler, uint8 flags)
 +
{
 +
  idt_entry[n].resreved = 0;
 +
  idt_entry[n].flags  = flags;
 +
  idt_entry[n].sel    = sel;
 +
  idt_entry[n].baseLo  = (handler) & 0x0000FFFF;
 +
  idt_entry[n].baseHi  = (handler) >> 16;
 +
  return;
 +
}
 +
</c>
 +
Diese (fehlerfreie) Funktion greift dabei auf ein Array aus folgendem struct zu:
 +
 +
<c>
 +
struct idt_entry
 +
{
 +
    unit16 baseLo;
 +
    uint16 sel;
 +
    uint8 always0; //reserved
 +
    uint8 flags;
 +
    uint16 baseHi;
 +
}
 +
</c>
 +
Und genau an dieser Stelle produziert der Compiler mit seiner Optimierung einen Fehler und die CPU wird sich mit einem freundlichen Triple-Fault verabschieden. Denn der Compiler hat die Eigenart, die Elemente eines structs an DWORD-Grenzen auszurichten, weil dann die CPU schneller arbeiten kann. Das hat in diesem Fall aber fatale Folgen, denn aus dem angegebenen WORDs/BYTEs macht der Compiler einfach mal DWORDs. Und damit ist natürlich der IDT-Eintrag komplett falsch. Glücklicherweise gibt es aber eine ganz einfache Lösung:
 +
<c>
 +
struct idt_entry
 +
{
 +
  //...
 +
}__attribute__((packed));
 +
</c>
 +
Das angehängte ''__attribute__((packed))'' vehindert, dass der Compiler die Elemente ausrichtet, wodurch schließlich der Code funktioniert.
